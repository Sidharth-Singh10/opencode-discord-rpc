## Repairs

### J1 — explicit schemas at every evidence sink

`src/m0/sanitize.ts` rebuilds snapshots, inspections, provenance, publications
(including refusals), runtime/locality/run documents, owner/acquisition rows,
and publisher diagnostics. `EvidenceLog` independently projects by sink name
before serialization. Capture/reference records have runtime schema checks and
are rebuilt; unknown event types map to `event.other`. Exceptions produce fixed
codes, never exception text. Unknown keys are not copied.

A string grammar alone is insufficient: API keys can look like identifiers.
M0 therefore keeps **reviewed finite vocabularies for model and provider
identities**, not arbitrary strings. The transmission spike recognizes the
OpenCode/OpenCode Go DeepSeek V4.1 Flash identities as vocabulary only;
`opencode/deepseek-v4.1-flash-free` is a harness test identity and no DeepSeek
model was executed. Variants use the
host's full `ReasoningEfforts` set — `none`, `minimal`, `low`, `medium`, `high`,
`xhigh`, `max` — plus its serialized `default` marker and absence; `null` means
"no variant" and is treated as absent rather than invalidating the identity.
Agents are user-defined in OpenCode config, so a finite list cannot be the rule:
built-in names (`build`, `plan`, `general`, `compaction`, `explore`) and custom
agent identifiers are admitted only by a documented shape — a single lowercase
identifier token of 1–64 characters from `[a-z0-9._-]`, starting with a letter.
Dots, underscores and hyphens are allowed inside that token. That is not free
text: it excludes `/`, `=`, whitespace, paths, queries and mixed-case
credential-shaped strings. **That shape check is not a credential filter.**
Because agent names are shape-admitted rather than reviewed, a lowercase
secret-shaped token such as `sk_live_abc123` or `ghp_16c7e42f` is accepted and
may be persisted to the 0600 evidence file. It is never placed in the Discord
activity payload. The "identifier-shaped secrets cannot reach evidence"
guarantee therefore holds for the model, provider, variant, tooltip, event and
diagnostic fields, not for `agent`. Anything outside these vocabularies refuses
publication. The newest assistant message is selected **before** sanitization.
Its model, provider, variant and agent are the only executed-provenance source:
a refusal names the failing field (`executed-model-unknown`,
`executed-provider-unknown`, `executed-variant-unknown`,
`executed-agent-unknown`), without borrowing an older supported assistant or
the session's current agent/selection. Identity, timestamp, payload and the
first ownership/anchor prechecks all run before any Discord socket is opened
for a fresh publication, so a refusal reached in that precheck window records
zero connections as well as zero frames. That guarantee is **not universal
after connect**: the in-transaction path can still refuse `not-owner`,
`revoked` or `busy` (recorded as `enqueue-not-owner`, `enqueue-revoked`,
`enqueue-busy`), and an in-transaction `anchor-conflict`/`anchor-pending`
`continue` re-enters the loop with the socket already open, where a later
precheck refusal can be recorded with a connection open. Packed zero-connection
assertions cover only refusals reached before the socket opens. Model/provider
extension is deliberately not a general registry; extending it is an explicit
future change. Numeric runtime versions and fixed host enums are separately
checked. The activity tooltip is independently checked before evidence output.

Tests inject credential containers, identifier-shaped credentials, private paths,
stack text, credential-bearing URLs and arbitrary event types into the metadata
sources and scan all plugin evidence files, including refused publications. The
suite also asserts the accepted agent boundary explicitly: `sk_live_abc123`,
`ghp_16c7e42f` and `xoxb-1234-abcd` are admitted agents and may appear in
private evidence. Validator diagnostics also avoid repeating invalid values and
unknown keys. Raw PTY transcripts and deliberately seeded fixture inputs live
outside plugin evidence; they are not privacy-safe exports.

### J2 — durable intent, serialized ACK reconciliation

Publication/disconnect commands serialize the entire sequence through ACK and
reconciliation. Every sequence re-reads authoritative anchor state.

1. A pending intent is committed **before** any socket enqueue.
2. A second `BEGIN IMMEDIATE` transaction checks owner + fence and authoritative
   committed/pending values, then synchronously enqueues the socket frame.
   **No await separates the ownership check and enqueue.**
3. Once a frame is enqueued, even a subsequent transaction-commit failure
   retains its request/nonce for ACK/timeout/closure reconciliation. It cannot
   be relabeled as a pre-enqueue refusal.
4. ACK-only reconciliation verifies both stored seconds and source milliseconds.
   Conflicting stored anchors fail; they are never silently accepted/overwritten.
5. Failed ACK persistence retains the acknowledged value in memory. The normal
   publisher timer retries; no external ticker is required. A conflict retains
   unresolved state rather than discarding it and adopting a newer value.
6. Durable pending intent is distinct from ACK-committed state. Reload/takeover
   conservatively reuse unresolved intent, never claim an unproven durable ACK,
   and cannot publish a conflicting newer anchor.

**Suspension limitation:** the guarantee is transactional ownership/fence
checking around synchronous enqueue, with serialized publication/ACK
reconciliation. It is **not** bounded takeover under arbitrary suspension. A
publisher stopped inside its SQLite write transaction can hold the writer lock
until it resumes or dies; lease expiry does not release it, and other instances
must fail closed. No unconditional takeover deadline is advertised or claimed.

**Tested suspension points:** the packed test suspends only after publication
completes — after the first publication has returned from ACK and its failed
persistence reconciliation, before the next publication — and kills after the
contender's publication has returned. Neither point deliberately suspends
inside an ownership/heartbeat transaction. The source subprocess lock-delay test
holds the write lock in a separate locker process; it demonstrates lock-delayed
takeover, not a publisher instrumented mid-transaction. There are no bundle test
hooks.

Pending reservations are conservatively retained after rejection or ambiguous
delivery. This may retain an older candidate after a rejected operation; it
prioritizes stable acknowledged anchors over reclaiming unused intent.
Across a crash between ACK and persistence, the durable intent preserves the
anchor, but the exact lost ACK is not claimed to have been durably recorded.

### J3 — correlated, unique operations

The strict validator correlates `(instanceId, nonce)` with exactly one enqueue
and one terminal. It checks matching command, attempt, pid, fence, session,
payload, phase/outcome and ordering. Duplicate and contradictory terminals,
unmatched ACKs, failed-phase successes and clear/publish substitutions fail.

It requires at least **five unique acknowledged publishes**, **two distinct
published sessions**, and explicit **unknown-session** and **unknown-identity**
pre-enqueue refusals. Post-enqueue rejection/timeout/closure is not a refusal
and never contributes to the quota. Positive fixtures include an authorized
nonce-bearing RPC rejection and repeated ACK persistence failures followed by
successful reconciliation.

### J4–J6 — locality, disposal, unknown namespace

- The entire advertised URL array is validated, including invalid/sparse
  members. Empty/null/whitespace/non-string/malformed/credential-bearing entries,
  unsupported schemes, and mixed local/non-local URLs refuse enrichment.
  IPv6 loopback is bracket-normalized without splitting on `:`.
- Pending connections are owned before handshake completion. Disposal marks
  work invalid, immediately closes pending/READY sockets, stops ownership and
  capture, then drains/closes evidence. Snapshot/disconnect continuations and
  queued commands cannot publish, reconnect, toast or write after disposal.
- Unknown identity refuses persistent-anchor publication **and enrichment**.
  `sessionAnchorKey` has no literal `"unknown"` namespace. Remote publication
  is also conservatively refused in this M0 implementation.

### J7 — retention follow-up

No anchor or pending row is automatically pruned. Expected growth is one
committed anchor per qualified session, plus unresolved pending intents; records
remain in the private runtime store across reloads and takeovers.

**M1-ANCHOR-GC:** specify retention, crash-orphan recovery and safe garbage
collection without allowing an acknowledged session's anchor to move. Until
then, do not delete the runtime store while any instance/card is active. No
arbitrary TTL/LRU was added in this repair.
